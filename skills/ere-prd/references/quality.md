# 信息充分性与质量判断

本文改写自 Product Idea Excavator 的产品发现/产品判断模块、PM-Skills 的 PRD/验收/异常模块及 prd-debate 的意图澄清/回溯校验。具体许可证和修改范围见技能内 THIRD_PARTY_NOTICES.md。

## 访谈什么时候结束

不是问完清单，也不是达到字数或轮数。结合文档与对话，六项核心信息能构成一条具体价值闭环即可进入草稿：

| 项 | 足够具体的内容 |
|---|---|
| user | 谁在什么场景触发任务；使用者、决策者不同时分别说明 |
| problem | 当前怎样完成，卡在哪里，影响是什么；真实需求证据与猜想分开 |
| goal | 用户要得到什么结果，怎样观察成功；没有基线/目标时说明测量计划 |
| scope | 最小有价值结果、本期包含与不包含的范围 |
| flow | 入口、前置条件、核心行动、输出与主要失败后的去向 |
| constraints | 已知重要限制、权限、依赖、时间/成本，以及哪些仍未知 |

三种状态：`sufficient` 有足够依据；`provisional` 有具体假设和验证方式，可写草稿；`critical_gap` 的不同答案将改变目标、范围、核心行为或重要风险，暂不能锁定方案。

提问之前先查现有材料。优先问当前决策价值最高的一个问题，不批量发问卷。记录为什么答案影响方案。同一问题一两次追问没有新事实，改用有差别的选项、现状实例、验证任务或待决项；不要继续原样问。关键问题不能靠“默认用户同意”解决，仍可分别写清可选路径的草稿。

访谈信息完整不等于需求已经验证。用户说“有趣”不是实际使用证据；内部改进、既有产品功能和创业探索也不共用固定付费/人数门槛。引用实际行为与文档，不编造调研、基线、市场数据、负责人或上线承诺。

## 方案与 PRD 的检查

推荐路径和一个真实备选路径足以支持普通功能取舍。必要时包括保持现状、人工验证、半自动流程；不要为凑方案数写明显无用的选项。优先最小闭环，区分核心价值、必要信任能力和以后功能。

逐需求检查 actor、trigger、behavior、outcome 是否能让读者重现行为。验收至少有 Given/When/Then、验证方法和验证角色。写观察得到的结果，避免“体验良好”“性能优秀”；指标若暂未定，不擅自编出阈值。

按实际影响评估权限拒绝、空输入/无数据、重复提交/并发、过期状态、依赖失败、失败重试与数据保存。适用项要关联需求；不适用项写具体理由。无需穷举所有可能异常，但不能删掉完成核心闭环所需的恢复能力。

出现模型生成或判断功能时，额外定义正常行为、拒答、不确定时的处理、兜底及各步骤评测方法、阈值和阈值依据。案例数从失败模式与覆盖需要推导，不沿用任意固定数量，也不把手工案例覆盖数当作总体失败率。

交给缺少作者背景的研发/外部协作者/执行 agent 时，说明权威资料及冲突处理、不能修改的边界及理由、每条需求的验证方式/角色、停下来向谁询问的条件。资料链接不能替代正文里必须知道的行为。

## 草稿、达标和可开工

`advance` 的结构检查与语义判断都要通过。语义判断逐项引用原文，解释为何充分或为何暂定。代码校验原文确实存在、来源当前、必要项完整；它不能判断模型的理由一定正确，主 agent 和独立评审仍承担语义责任。

进入草稿可以携带暂定需求证据；研发交付不能携带尚未决定的核心行为、权限、恢复和验收。`material:true` 的未决项阻止 resolve，通过 `draft-export` 交付缺口与验证计划即可，不强迫用户完成不必要调研。

评审 blocker 看影响，不能靠其他改进意见的数量稀释。对已确认承诺逐条验证原文保留；删除、缩小或反转优先级都不能由两个模型投票通过。用户明确改变需求时，将决定作为新来源登记，重新走受影响阶段。

## 语义闸门

`quality-template` 给出本阶段的具体检查 ID。每项填写 `status`、`reason`、`anchors`，anchors 是当前阶段产物或 PRD 的真实片段。

- pass：判断成立，并说明依据。
- provisional：仅 discovery/solution 允许，写具体假设与验证，不当作验证成功。
- fail：仍有实质问题，阻止推进。
- not_applicable：仅条件契约、无图时的视觉一致性/可读性、无目标空间时的目标适配允许，并说明为何条件不触发。

不设置“总分达到 80”或“章节足够多”的闸门，也不让轮次用尽强制达标。
